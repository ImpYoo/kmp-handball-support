# Generator-Grade Prompt: Handball Table Official Evaluation REST API

## Role

You are a senior Kotlin backend developer and API designer.

Generate the REST API layer for the Handball Table Official Evaluation application.

## Source Of Truth

This document is the source of truth.

If any parts of this prompt appear to conflict, use this precedence order:

1. **Detailed Specifications**
2. **Deliverables**
3. **Cross-Cutting Rules**
4. **Examples**
5. **Background text**

Do not infer requirements from earlier iterations when they conflict with this document.

## Goal

Build a Ktor-based REST API that:

- accepts requests via DTOs
- maps DTOs into the domain/application layer
- stores evaluations initially in a JSON file
- exposes read endpoints for stored evaluations
- returns problem-style error responses
- keeps domain and transport models separated

## Scope

The API covers:

- application bootstrap
- DTO request/response models
- DTO-to-domain/application mapping
- application service orchestration
- ID generation
- file-backed repository adapter
- REST endpoints
- problem-style HTTP error handling
- integration tests

## Non-Goals

Do **not** generate or introduce:

- database persistence
- authentication or authorization
- pagination
- update/delete endpoints unless explicitly requested
- OpenAPI generation
- client SDKs
- UI code
- moving DTOs into `shared`
- leaking serialization concerns into the domain module

## Technical Constraints

- Server module: `server`
- Framework: Ktor
- Language: Kotlin JVM
- Domain module dependency: `shared`
- DTOs must live in the `server` module, not in `shared`
- Domain objects must not depend on API DTOs
- Repository implementation may use `kotlinx.serialization` for JSON file storage
- Use RFC7807-style problem responses (`application/problem+json`) as a Zalando-aligned baseline

## Architectural Rules

1. Keep the boundary layers separate:
   - DTOs in API layer
   - orchestration in application layer
   - invariants in domain layer
   - persistence in repository adapter
2. Request DTOs must not contain repository/application-generated IDs.
3. New evaluation IDs must be generated by an application service or dedicated ID generator, not by the request DTO.
4. The repository should remain focused on persistence and uniqueness enforcement.
5. The API must communicate only through DTOs, never raw domain objects.

## Domain Assumptions

The API must work against the current domain model under:

`de.exhumedo.kmp.handball_support.domain.rating`

Relevant assumptions:

- `PerformanceEvaluation` is the aggregate root
- `PerformanceEvaluation.create(...)` requires explicit `id`
- `EvaluationScore` contains:
  - `appearance`
  - `influence`
  - `teamwork`
- weighted totals are derived by `EvaluationScore.toScore(...)`
- the table team contains:
  - `timeKeeper`
  - `scoreKeeper`
  - optional `delegate`

## Detailed Specifications

### `Application.kt`

Responsibilities:

- define the server entrypoint
- configure the Ktor application
- wire:
  - repository adapter
  - application service
  - `Clock`

Defaults:

- host: `0.0.0.0`
- port: `8080`
- default storage file path:
  - from env var `PERFORMANCE_EVALUATIONS_FILE`, or
  - from system property `performance.evaluations.file`, or
  - fallback to `server/data/performance-evaluations.json`

### `api/Http.kt`

Responsibilities:

- install `ContentNegotiation`
- install `StatusPages`
- configure JSON serialization
- return problem-style JSON errors

Error format:

- content type: `application/problem+json`
- response DTO:
  - `type`
  - `title`
  - `status`
  - `detail`
  - `instance`

Map these failures:

- duplicate game evaluation -> `409 Conflict`
- domain validation failures -> `400 Bad Request`
- generic `IllegalArgumentException` -> `400 Bad Request`
- unexpected exceptions -> `500 Internal Server Error`

### `api/Routing.kt`

Endpoints:

- `GET /`
- `GET /health`
- `POST /api/performance-evaluations`
- `GET /api/performance-evaluations`
- `GET /api/performance-evaluations/{id}`

Optional query patterns on list endpoint:

- `?gameId=...`
- `?firstRefereeId=...&secondRefereeId=...`

Rules:

- `POST` accepts request DTO, maps to application command, calls application service, returns response DTO
- `GET /api/performance-evaluations`:
  - if `gameId` is present, return the single matching evaluation or 404
  - if both referee IDs are present, return all matching evaluations
  - if only one referee ID is present, return `400 Bad Request`
  - otherwise return all evaluations
- `GET /api/performance-evaluations/{id}` returns single evaluation or 404

### `api/dto/ProblemDto.kt`

Type:

- serializable DTO for problem responses

Fields:

- `type: String`
- `title: String`
- `status: Int`
- `detail: String`
- `instance: String`

### `api/dto/PerformanceEvaluationDtos.kt`

Responsibilities:

- define request/response DTOs
- define nested DTOs for game, person, role assignment, referee pair, table official team, and score
- map request DTOs into application commands
- map domain aggregates into response DTOs

Rules:

- `CreatePerformanceEvaluationRequestDto` must **not** contain `id`
- response DTO should contain:
  - `id`
  - `game`
  - `refereePair`
  - `tableOfficialTeam`
  - `score`
  - `weightedTotalScore`
  - `comment`
  - `createdAt`
- `weightedTotalScore` should be computed via `score.toScore()`

Official role transport values:

- `FIRST_REFEREE`
- `SECOND_REFEREE`
- `TIME_KEEPER`
- `SCORE_KEEPER`
- `DELEGATE`

### `application/CreatePerformanceEvaluationCommand.kt`

Type:

- simple application command object

Fields:

- `game: Game`
- `refereePair: RefereePair`
- `tableOfficialTeam: TableOfficialTeam`
- `score: EvaluationScore`
- `comment: String?`

All command fields use domain types from `de.exhumedo.kmp.handball_support.domain.rating.model`.

### `application/PerformanceEvaluationApplicationService.kt`

Responsibilities:

- orchestrate creation of new evaluations
- generate IDs through an abstraction
- create domain aggregate
- persist via repository

Requirements:

- depend on:
  - `PerformanceEvaluationRepository`
  - `EvaluationIdGenerator`
  - `Clock`
- expose:

```kotlin
suspend fun create(
    game: Game,
    refereePair: RefereePair,
    tableOfficialTeam: TableOfficialTeam,
    score: EvaluationScore,
    comment: String?,
): PerformanceEvaluation
```

Also define:

- `fun interface EvaluationIdGenerator`
- default implementation `UuidEvaluationIdGenerator`

ID generation rule:

- use Kotlin stdlib UUID support

### `persistence/JsonFilePerformanceEvaluationRepository.kt`

Responsibilities:

- implement `PerformanceEvaluationRepository`
- store evaluations in a JSON file
- create the storage file/directories if missing
- support read/write of all persisted evaluations
- enforce uniqueness of one evaluation per game

Rules:

- JSON file stores serialized persistence records, not domain objects directly
- repository maps persistence records to/from domain objects
- saving an evaluation for the same game but a different evaluation ID must fail with a dedicated conflict exception
- saving the same evaluation ID again should update the existing record

Persistence exception:

- add a repository-level exception for duplicate game evaluation conflicts

### Tests

Generate integration tests that cover at least:

- root endpoint responds successfully
- health endpoint responds successfully
- creating an evaluation returns `201 Created`
- created evaluation can be fetched again
- listing all evaluations returns stored items
- filtering by `gameId` returns the matching evaluation or `404`
- filtering by `firstRefereeId` and `secondRefereeId` returns matching evaluations
- providing only one referee-pair filter parameter returns `400`
- `createdAt` comes from injected clock
- duplicate evaluation for same game returns `409 Conflict`
- requesting a missing evaluation by `id` returns `404`
- problem responses are returned for invalid requests

## Zalando Alignment

Use these conventions as the practical baseline:

- clear resource-oriented endpoints
- JSON DTOs only at the HTTP boundary
- RFC7807-style problem responses
- meaningful HTTP status codes
- explicit separation between transport, application, domain, and persistence concerns

Do not attempt to fully implement all Zalando tooling or spec artifacts unless explicitly requested.
